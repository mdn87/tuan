## What Tuan Is

Tuan is a standalone Lugos project for agent-work measurement, context-impact estimation, and usage forecasting. It preserves a trustworthy history of what was requested, what was expected, what context was supplied, what actually happened, and what the complete workflow consumed—then uses that history to improve forecasts and evaluate context strategies across agents, models, and repositories.

The name is **Tuán mac Cairell**, who preserves and recounts history across successive transformations. The package and submodule are both `tuan`.

### Ecosystem Ownership & Boundaries

| Component | Responsibility |
| --- | --- |
| **Tuan** | Normalize operational evidence; retain append-only history; build rebuildable analytical views; issue forecasts, findings, and reports; evaluate their usefulness and cost. |
| **Sulis** | Own durable memory content, capture, and recall. Supply versioned metadata and identifiers; Tuan never writes memories or duplicates their contents. |
| **Torc** | Own continuity, context construction, and context projection; serve as the source of prior efficiency research. Supply context manifests and policy/version metadata. |
| **Autowork & Harnesses** | Own task admission, scheduling, execution, routing, and any later approved intervention. Supply run lineage, checkpoints, and outcome evidence. |
| **Source Telemetry & Audit** | Remain authoritative for raw provider counters and closure receipts (`lugos-audit`, which attests repository hygiene at closure, not task behavior or acceptance). Tuan preserves provenance and reconciles definitions across sources. |

Tuan is not a second memory store and does not orchestrate execution. Its initial interfaces are local library functions, versioned schemas, and a CLI (`tuan`). Automatic memory edits, context tuning, agent routing, dashboards, and long-running background services are out of scope for the initial design and remain disabled until Milestone 5 defines their safeguards.

## Core Questions & Ground Rules

Tuan keeps three questions strictly separate:

| Capability | Question it answers | Key distinction |
| --- | --- | --- |
| **1. Observation** | What context, usage, active work, elapsed time, and outcomes occurred? | Direct accounting with provenance; missing is `unknown`, never `0`. |
| **2. Forecasting** | Given only the information available at a checkpoint, what total or remaining usage should we expect? | `Forecast − actual` is forecast error, not context savings. |
| **3. Attribution** | Compared with a specified baseline, what difference can reasonably be attributed to a context strategy or observer intervention? | Smaller initial context is not automatically lower total effort; cheap failure is not efficiency. |

### Reporting Rules

- Lead with the strongest supported measurement or estimate. Label every quantity **observed**, **estimated**, **experimental**, or **unknown**. Name the comparison baseline, accounting scope, and reporting period.
- State each material limitation once, then name the smallest next measurement that would reduce it. Never substitute a blanket "cannot prove savings" disclaimer for the quantified evidence already in hand.

### Evidence, Privacy, and Storage Rules

- **Storage architecture**: This is the proposed D3 topology. If D3 selects another topology, revise the affected receipt rules and M1 recovery cases in the same accepted decision before real ingestion.
  - **SQLite** is the canonical ledger: one single-writer database per host, authoritative for every record produced on that host (events, forecasts, corrections, allocation entries, deletion and expiry receipts), stored outside the git checkout and outside live file-synchronization folders; never sync a live SQLite file across hosts. Analytical projections are disposable tables rebuilt from ledger records under a versioned transformation.
  - **JSONL** supplies versioned exports for collection and recovery. A complete recovery set includes event/history streams plus a separately protected stream of refusal, expiry, and representation-revocation authority, with a manifest binding the streams and their boundaries. Operational exports and backups retain the required access controls; real refusal keys never enter committed fixtures, which use invented keys and sanitized records in the same formats. Recovery validates the complete set and loads maintenance authority in a first pass before admitting history. Missing authority means incomplete recovery, never an assumed empty refusal set. Collection to `lugos-host` carries protected authority under the accepted policy; an authorized origin can revoke its own records and their dependent copies in Tuan-owned collection ledgers/backups, not unrelated origins.
  - **Shared database / collector service** is deferred until measured multi-host concurrency demands it.
  - **Writer coordination**: All mutating commands share one interprocess ledger lock, bounded waiting, and a visible busy result. Test contention and recovery after interruption on each supported platform; no daemon is needed.
- **Append-only and idempotent**: Re-importing the same event is idempotent. A duplicate identifier with differing content is an explicit conflict, never a silent overwrite. Corrections append a superseding record while keeping original forecasts and observations inspectable, except for authorized privacy removal. Unknown schema versions or malformed records fail visibly or enter a sanitized quarantine.
- **Redaction before persistence**: Redact and allowlist fields before any persistence, including quarantine and rejection logs. Persist metadata and access-controlled references by default; never persist secrets, credentials, hidden reasoning, or unrestricted prompt, response, or memory contents. Payload capture requires an explicit purpose and opt-in retention class (off by default). Every normalized event records its redaction-policy version. Duplicate comparison uses the same source identity and policy version; a version mismatch requires either a verified transformation of retained metadata or authorized re-acquisition from the authoritative source under the new policy, otherwise sanitized rejection. Re-acquisition records evidence that this is the same immutable source event/content (a dedup key alone is insufficient), acquisition provenance, and the superseded representation link. Missing content-identity evidence stays a conflict or coverage gap; policy changes cannot reintroduce facts subject to deletion. A version change never legitimizes differing content automatically. Source event identity stays stable across redaction versions; normalized representation identity changes. An explicit verified policy migration supersedes the representation with a new immutable record and provenance link. Accounting and projections select one applicable representation per source event, so migration/re-acquisition cannot double-charge usage. Re-acquisition uses the current policy. Privacy-required cleanup revokes and purges the old representation through recorded managed-copy cleanup, without treating representation-only revocation as deletion of the surviving source event or subject.
- **Retention and deletion**: Operational retention has a **90-day floor**; D4 sets the accepted duration (proposed: **180 days**). Authorized privacy deletion overrides retention. Set a storage quota and warn before it threatens that window; never silently discard evidence to satisfy a quota. Retention applies to local exports and backups as well as the database, and reports state which evidence has expired and which replay claims remain possible. Append-only semantics prevent silent history rewriting; they do not override authorized privacy deletion, which must purge matching records, projections, exports, and managed backups across Tuan-owned storage classes while retaining a non-sensitive completion receipt and the minimum protected refusal state permitted by the deletion policy; producer-owned originals outside Tuan's authority are reported as remaining, never assumed purged. Compact evidence records may belong to a longer retention class than operational records (decided before the first real M1 import); authorized privacy deletion applies across every class, including superseding scores, projections, and other derived records, and subsequent rebuilds or maintenance cannot resurrect records matching retained refusal keys.
- **Deletion refusal contract**: Completion receipts contain operation ID, authorized origin/scope, time, counts, and cleanup status without subject values. A separate access-controlled refusal record retains producer-scoped opaque subject keys and known event/deduplication keys under an accepted retention/access policy; pseudonymous keys are not non-sensitive. Restore loads this authority before older records. New event IDs for a known subject remain refused; an unmapped new subject identity is an explicit recognition limit. Foreign refusal records require an established authority mapping. The refusal namespace is the configured source/owner authority, independent of whether the producer host or PID was observed; unknown physical producer identity does not remove stable source-event matching. If a trustworthy source namespace or subject mapping is missing, quarantine unscoped input or match only known event keys, and report the recognition limit. If refusal keys expire or must be erased, retain a non-subject namespace restriction and reject unverifiable imports in that namespace, including later-position records that could reintroduce a deleted subject. Reopening admission requires re-established refusal coverage or an explicitly authorized scope change; a newer timestamp or position is insufficient.
- **Strict temporal cutoffs**: Every event records both *event time* and *ingestion time* in UTC alongside source clock quality and sequence numbers. Preserve known parent-child relationships; never invent them from proximity in time, and use sequence and lineage evidence where clocks disagree. A source timestamp earlier than a prediction is insufficient if the record had not been received by the forecasting ledger when the prediction ran. Late arrivals update later reports but never enter an earlier checkpoint's feature snapshot. Retrospective replays must be explicitly labeled; never manufacture a prospective forecast by backdating one.
- **Ledger identity across hosts**: Identify every receipt boundary by ledger identity and position together. Recovery preserves historical ledger identities and positions as immutable receipt provenance; before accepting new writes, each restored database atomically records a fresh writer-ledger identity linked to the recovered boundary. Two restores cannot continue the original writable identity. Positions are monotonic within each writer identity; collection into an existing ledger assigns receiving positions while retaining origin references. Imported forecasts retain their original provenance, never acquire a receiving cutoff by reusing an origin's integer position, and remain excluded from verified prospective comparisons when origin issuance cannot be established. Preserve the original claimed forecast kind and record imported issuance verification separately as verified, unknown, or invalid. Across ledgers, receiving order and wall-clock timestamps alone cannot prove issuance preceded the outcome: require origin cutoff/acquisition evidence plus a trustworthy causal link or ordering attestation connecting issuance to the later outcome. For a same-origin pair, an integrity-checked export must establish the original issuance cutoff, acquisition/lifecycle coverage, and ordering of issuance before the target terminal event as well as its later label; mere forecast-before-label receipt order is insufficient. Cross-origin evidence needs an explicit causal ordering link; otherwise verification is unknown and the claim is excluded. M0–M2 need not implement a distributed ordering service.
- **Acquisition evidence**: Record the source/profile version, acquisition time and mode, bounded source generation or prefix, and observed or unavailable field coverage. Historical imports admit all evidence in the acquired batch before classifying new forecasts. Replaying checkpoint rows ahead of already-acquired outcomes cannot establish prospective issuance. Incremental acquisition must establish what was available when a forecast was issued; gaps and unsupported source versions remain explicit. Prospective eligibility depends on the target signature’s source-side terminal event, separately from when acceptance or a numerical label is recorded: qualified lifecycle evidence must establish the target was still open at issuance. A known terminal event or already-known final target makes a new estimate retrospective; absent trustworthy lifecycle evidence, issuance verification is unknown and excluded from prospective scoring. An open task that later consumes zero additional tokens is not disqualified merely because its last usage happened before the forecast.

### Accounting Rules

- **Provider-specific token categories**: Store input, output, cache-read, and cache-write counts separately with provider definitions. Cache counts are often subsets of reported input totals—never sum counters blindly.
- **Single-charge reconciliation**: Reconcile parent aggregates against an authoritative call-level source so cumulative-counter snapshots, retries, and parent/child calls never charge the same work twice. Counter resets are explicit discontinuities, not negative consumption.
- **Whole-workflow scope**: Include failed and abandoned attempts, retries, child calls, context preparation, retrieval, summarization, maintenance, and observer/reporting overhead. Report coding execution and observer overhead separately, plus an explicit whole-workflow total.
- **Reusable preparation allocation**: Track shared preparation in an allocation ledger (direct cost, allocated shares per task, allocation rule/cohort, and unallocated overhead). Never charge both full shared preparation and its allocated shares in the same total.
- **Distinct units**: Keep tokens, dated-rate monetary estimates, actual billing, subscription allowances, wall-clock elapsed time, active work, identifiable wait states (user, provider queue, build), and human effort distinct. Overlapping child durations cannot be summed into wall time; unobserved waiting or human effort stays unknown. Do not treat token counts across different model/tokenizer families as interchangeable effort units.
- **Quality pairing**: Track completion and quality alongside usage. Keep failed, abandoned, and in-progress runs in the history without treating unfinished cost-so-far as a cheap completed task.
- **Estimate and score lineage**: Keep four record kinds distinct and never substitute one for another: **original forecast** (what a predictor emitted at a checkpoint under its information cutoff), **recorded actual** (the labeled outcome with its label version), **recalculated score** (a scoring-rule version applied to preserved forecasts and actuals under the Score contract; preserves earlier scores and supersedes prior labels within a compatible rule/policy series), and **revised estimate** (a newer predictor, training snapshot, or predictor-input transformation replayed against a historical checkpoint; always `retrospective_replay` with a leakage status). Evaluation-only changes rescore unchanged predictions; a change that alters predictor inputs requires new predictions, which are revised estimates. A revised estimate is never scored as prospective forecast accuracy, whatever its leakage status, and never stands in for a missing actual; comparing two estimates measures their agreement only. A missing actual stays `unknown`.

## Minimum Record Contracts

| Record | Required information |
| --- | --- |
| **Event envelope** | Immutable source content: event/schema/source versions; stable event ID and source deduplication key; UTC event time and source sequence; event type; task/run/attempt/session/agent IDs; parent link; producer host (`lugos-link` slug), process start time, and PID where observed, otherwise explicit unknowns and coverage; namespaced stable source session/event identity or documented source-generation/offset identity for deduplication; provenance reference; redaction status and policy version. Separate ledger receipt: collector identity, UTC ingestion time, and a monotonic ingestion position in the receiving ledger. Duplicate-content comparison covers normalized source content under the recorded redaction policy, excluding receiving receipts; the receiving ledger's receipt governs checkpoint cutoffs. |
| **Task / run** | Request reference and version; task family and repository; acceptance criteria and revision; provider/model/settings; lifecycle state; parent-child lineage; context policy/strategy version and other configuration identifiers recorded as *observed in effect* for the run (declared-versus-observed provenance flagged; mid-run changes ordered by event sequence), never inferred from a decision's acceptance date; applicable decision references (namespaced decision ID, immutable revision, lifecycle status at run start, applicability source) when a producer or operator supplies them. Missing links are explicit; `unknown` is a valid value. |
| **Usage observation** | Provider call ID; accounting scope and role (`coding`, `preparation`, `observer`, `reporting`); reported metric categories/units; delta vs. cumulative semantics; measurement provenance/quality; dated rate or billing reference if available. |
| **Checkpoint** | Deterministic checkpoint ID from task/run, acquisition or derivation kind/version, relevant source receipt frontier, observed code/spec/context identities, and feature-snapshot version. Repeating an acquisition with unchanged evidence returns the existing checkpoint and original cutoff; forecast/score writes or unrelated maintenance alone do not create a new checkpoint. Available-through ingestion boundary and source positions; task/spec/plan revisions; git commit SHA plus patch hash for uncommitted work; context references; test results and usage known so far; feature snapshot and version. |
| **Forecast** | Target (`total_input_tokens`, `total_output_tokens`, `remaining_input_tokens`, etc.), units, and a versioned target signature (included roles, lineage scope, allocation-policy version, terminal event, label-availability rule); checkpoint ID and information cutoff; prediction timestamp; deterministic forecast binding from checkpoint ID/cutoff, complete target signature, estimator/configuration version, training-snapshot version, predictor-input transformation version, and forecast kind; unchanged bindings return the stored forecast before inference. Issuance verification (`verified`, `unknown`, `invalid`) and evidence references are append-only assessments separate from the immutable original claim; estimator and training-snapshot versions; for every forecast kind, training data, fitted input transformations, and features must be bounded by the checkpoint’s information cutoff to qualify as cutoff-respecting. Reject a prospective issuance using a later bound; an explicitly requested replay may instead retain that mismatch as contaminated. Reusing a checkpoint never permits newer training information. Point estimate and empirical/calibrated range (or `insufficient_history`); assumptions; inference cost and latency; forecast kind (`prospective` or `retrospective_replay`) and, for replays, a leakage status: `cutoff_verified` (training-snapshot and feature-snapshot bounds demonstrably at or before the checkpoint's information cutoff), `contaminated` (training or features known to include the task's outcome or later records), or `unknown` (provenance unavailable; never upgraded without evidence). Revisions link to prior forecasts without overwriting. |
| **Outcome** | Terminal status (`completed`, `failed`, `abandoned`); ongoing status and cost-so-far belong to Task/run lifecycle observations, not a terminal Outcome. Acceptance evidence (test output, verification records; a `lugos-audit` receipt attests hygiene, not acceptance) and assessed code/spec revision; final target cost with its label version; quality assessment; outcome-known timestamp; linked rework updates, keeping later operational spending apart from corrections to spending inside the closed target and preserving every label version. |
| **Score** *(derived, M2)* | Deterministic binding: forecast ID (or fixed aggregate membership), outcome ID and label version, complete target signature, metric, scoring-rule implementation/configuration version, and applicable policy ID/version. Before scoring, an as-of-dependent policy derives a deterministic anchor from the ordered eligible input population, selected labels, and policy window membership/weights; include that anchor in its binding. Unweighted bindings have no window anchor. Invocation time alone never creates a new binding; repeated-run timing is an operational receipt. Record evaluation time and supersession provenance separately. An unchanged binding returns the stored score. Current views resolve the applicable label for each forecast/target/metric within a rule-and-policy series; corrected labels supersede the older label result in that series. Historical-as-of results cannot replace newer current results. Incompatible series remain separate and the unweighted reference is retained. |
| **Finding** *(M4)* | Claim; affected requirement or file/line location; evidence references; inspected revision; expected consequence; suggested verification; observer version and cost; advisory disposition (`surfaced`, `deduplicated`, `stale_revision`, `dismissed`). |
| **Intervention** *(M5)* | Finding or policy reference; advice shown and timestamp; actor/decision; action taken; policy revision; verified result; rollback reference. |

### Planned Interfaces

- **Adapter**: source records → validated normalized events with provenance and import coverage.
- **Projector**: retained events + transformation version → reproducible analytical views.
- **Predictor**: checkpoint + explicitly bounded training snapshot → independent forecast or explained unavailable result.
- **Reporter**: versioned views + report scope → machine-readable JSON and readable Markdown.
- **Observer** *(M4)*: checkpoint + bounded evidence → revision-specific findings, with no authority to modify the task.

Compare predictors on the same target, checkpoint, and information cutoff, and save each original output before exposing any peer output. Physical parallel execution is optional; independence and comparable inputs are the requirements.

### M3: Live Checkpoint Capture & Deterministic Rule Signals

**Outcome**: Accumulate routine operational history for D6 data sufficiency with bounded, measured collection overhead.

1. Wire lightweight checkpoint emission into the D2 workflow (using existing lifecycle hooks or file exports, not a persistent daemon) at six meaningful events:
   - `plan_ready`, `patch_produced`, `repeated_test_failure`, `scope_change`, `compaction_or_handoff`, `completion_claimed`.
2. Add deterministic, zero-LLM **loop and risk detector rules**:
   - Repeated reads of unchanged files after a context reset;
   - Identical test failure repeating without a changed assumption;
   - Reverting and recreating substantially similar patches;
   - Diff growth while acceptance criteria remain unresolved;
   - Growing effort spent recovering previously supplied information;
   - Completion claimed while an explicit requirement has no verification evidence.
   *(Each rule emits an inspection signal, never an automatic failure verdict.)*

   **Checkpoint evidence**: Each derived checkpoint records its source-event references, derivation version, inspected revision or context epoch, and receiving-ledger cutoff. The following prerequisites must be available from the selected source or explicit operator metadata:

   | Checkpoint | Evidence required before emitting it |
   | --- | --- |
   | `plan_ready` | An identified plan revision is explicitly finalized or accepted; saving a draft is insufficient. |
   | `patch_produced` | A successful change with distinct before/after revision or content identities; a failed edit is insufficient. |
   | `repeated_test_failure` | Distinct completed failing invocations with comparable test identity, revision, and failure evidence; duplicate log rows are insufficient. |
   | `scope_change` | An explicit change to the request or acceptance-specification revision; editing the implementation plan alone is insufficient. |
   | `compaction_or_handoff` | A recorded context transition; elapsed time, a counter reset, or a collector restart is insufficient. |
   | `completion_claimed` | A task-level claim bound to the inspected revision; message completion and end-of-file are insufficient. |

   **Rule evidence**: Each rule returns `fired`, `clear`, or `unavailable`, with its version, evidence references, inspected revision, and cutoff. A `clear` result requires coverage of the relevant evidence window. Missing inputs produce `unavailable`, not a negative finding. Repeated-read rules require unchanged content identities and an observed context reset; failure rules require comparable invocation and failure identities; recreate rules require a connected revision history; growth rules require a common diff base and explicit acceptance progress; recovery rules require identified recovery work and comparable measured costs; completion rules require the applicable checks and verification at the claimed revision. Test-pass counts alone do not measure acceptance progress. Choose and version thresholds when the source is qualified rather than importing unmeasured constants.

   Every supported derivation and rule gets positive, nearby-negative, missing-input, duplicate-event, and late-evidence cases. Later evidence can produce a new assessment but cannot rewrite an old checkpoint or signal. These requirements sharpen M3; they do not add M3 rules or live emission to the M0–M2 release.

3. Add **`tuan refresh`**, an idempotent maintenance verb. It derives pending work from durable **evaluation-coverage records** (which forecasts and lineages have been scored under which scoring-rule and policy versions), kept independently of projection progress so scoring missed after a projection advance or an interruption is rediscovered: new events or newly known outcomes → project and score affected lineages; changed issuance-verification assessments → invalidate affected eligibility/coverage and rebuild comparison membership; authorized deletion receipts → invalidate coverage after the authorized purge across classes and recompute eligible surviving aggregates; operational expiry → invalidate only claims needing expired inputs, retaining self-contained compact evidence when adopted and marking recomputation/replay unavailable where inputs expired. Retained scores are not automatically current: their applicability still requires surviving label/version and exclusion evidence; a changed evaluation-only scoring rule → recalculated scores in a separate versioned series linked to the prior series; a changed predictor-input transformation or predictor version → retrospective revised estimates only when explicitly requested; a crossed recency-window boundary → refreshed weighted scores; nothing relevant → a recorded no-op. Score identities are deterministic so repeats are retry-safe, and coverage progress commits only after a unit's scores are durably written. Evaluation coverage is canonical ledger metadata in the operational class unless an accepted compact class covers it. Refresh receipts (changes, versions, duration) are bounded operational diagnostics outside the evidence ledger. Assign both classes before first use; their records, exports, and backups obey subject deletion, expiry, and dependency invalidation. Invocation-receipt-only changes never count as pending work. It never retrains or promotes a predictor and never modifies ledger originals; running it from cron on `lugos-host` is an operations decision taken after its cost is measured here, and it remains a periodic batch, not a service.
4. Add an opt-in, versioned **recency-weighting policy** for scorecards, off until a recorded decision selects it; the unweighted score stays the reference and promotion criteria stay unweighted. For evaluation, freeze both the receiving-ledger identity/position boundary and the window-reference time. Admit only evidence received through that boundary; source outcome times alone cannot admit late records. Replaying an evaluation reuses both values. A clock-driven refresh may advance the window-reference time without new source events, while unchanged selected inputs/weights still reuse the same score binding. The policy and each weighted score's evaluation identity fix the window size and basis (outcome-known time, or completed-lineage count with deterministic ordering), the deterministic input/window anchor defined by the Score contract, the frozen evidence boundary and window-reference time as provenance, the eligible cohort and lineage population, the contribution unit, and the label-selection rule; late outcomes and corrected completion times create a new as-of evaluation rather than rewriting an earlier one, so a current reassessment stays distinguishable from a historical-as-of result. Weights are group-normalized so a stated split (such as 65/35) holds regardless of group sizes, which is disclosed as intended; first check recent support: below its declared minimum, including an empty recent group, suppress the weighted score as `insufficient_recent_support`; only with sufficient recent support and an empty older group does reporting fall back to the unweighted score with an explicit note.

**Exit criteria**: Source-to-ledger reconciliation survives process restarts and reconnects without duplicate charges; collection errors fail open for the coding agent while surfacing visibly in Tuan; missed events, ingest latency, storage growth, and overhead are measured against a declared budget; configured retention is verified with controlled timestamps; prospective evaluation cohorts are established before predictors are judged; each supported checkpoint event has a trigger test; each supported rule declares its required metadata, predicate or threshold, and behavior when inputs are unavailable, with the positive, nearby-negative, missing-input, duplicate-event, and late-evidence cases required above for both derivations and rules; rules whose inputs are unavailable are deferred rather than reading missing evidence as no risk. Releasing does not require waiting 90 days. Refresh runtime, storage growth, and no-op cost are measured against the declared budget; tests cover already-projected but unscored events, interruption between projection and scoring, late outcome corrections, deletion versus operational-expiry behavior on the same lineage (with and without sufficient compact evidence), invalidation with unchanged maximum source-event position, repeated execution, and a no-op that leaves canonical ledger records and projection contents logically identical while writing only its operational receipt. Compare deterministic row/content hashes or canonical exports rather than SQLite file bytes; no-op refresh adds no semantic records and reruns no inference. Weighted-score tests cover a window-boundary crossing, a late correction, multiple forecasts in one lineage, the minimum-support and empty-group boundaries, and rebuilding the same frozen evidence-boundary/window-time evaluation after a late outcome with an earlier source timestamp arrives; the late outcome cannot enter that historical population.

### M4: Bounded Semantic Observer & Advisory Stage

**Outcome**: Measure whether one narrow LLM reviewer adds confirmed value beyond deterministic rules.

1. Add one semantic observer with a single narrow job—detecting **unsupported completion claims or requirement drift**—invoked only at selected completion/patch checkpoints under a strict cost cap.
2. Enforce observer isolation: record the observer's raw finding before exposing any peer output; bind every finding to the exact code revision inspected; use an isolated git worktree/checkout if verification runs tests.
3. Add the single **advisory stage** that deduplicates findings, checks whether the inspected revision is still current (requiring revalidation if relevant code changed), and decides what to surface (in shadow mode first).
4. Score the observer on **confirmed findings, missed problems on adjudicated samples, false alarms, useful warning lead time, interruptions, and token/latency cost** (never agreement rate). Preserve findings that prompted a fix as confirmed true positives rather than relabeling them false alarms after the defect disappears.
5. Define, without scheduling, two decision-aware finding types for later specialists under the "measured gap" rule: **`decision_conflict`** (a patch or run contradicts a decision accepted and not superseded at the inspected revision's time; cites decision ID and revision, affected location, and expected consequence; deterministic where the decision carries a machine-checkable constraint, otherwise semantic) and **`revisit_proposal`** (a divergence-register or decision reconsideration trigger appears satisfied by retained evidence; cites the original decision or compromise, the evidence that its constraint changed, affected components, and estimated effort and benefit). Both are advisory and bound to the inspected revision like every Finding.

**Exit criteria**: The observer detects seeded unsupported claims, leaves a supported claim unflagged, preserves a stale result against its original revision, and requires revalidation when relevant code changes (functional checks); rules and the semantic observer are then scored on the same bounded checkpoint sample with independently adjudicated positive and negative cases, reporting incremental confirmed findings, misses, warning timing, duplicate findings, and added cost with explicit denominators—zero or negative incremental value is an honest result. Requires reliable M2 records and an explicit model/cost choice before any paid call. Add other specialists only for a measured gap; the execution system remains responsible for any response to advice.

### M5: Attribution Studies, Ensembles, and Controlled Improvement Loop

**Outcome**: Answer specific context-impact questions at stated confidence levels and govern any policy recommendations.

1. **Attribution progression**: Move from descriptive reporting → clearly labeled observational comparisons (with declared matching/adjustment variables and confounders) → human-approved matched or randomized task-lineage trials under `docs/studies/`.
2. **Separable causal questions**: Keep four questions distinct in every study protocol:
   - Does the context treatment itself reduce total effort or improve quality?
   - Do observer warnings/interventions help?
   - Does the combined workflow justify its total preparation + coding + observer overhead?
   - Did the expected benefit stated in a decision record materialize, measured as that record's Measurement field specifies, with its causality caveat?
3. **Ensembles**: Evaluate predictor ensembles only after M2–M3 history measures individual predictor error correlation across cohorts.
4. **Governed improvement ("self-healing" contract)**: Progress from reports → recommendations → human-approved context-policy experiments. Any future automatic policy adjustment requires a written contract specifying: what signal detects a problem, the bounded parameter allowed to change, versioned policy IDs, quality guardrails, an independent evaluation holdout that the policy cannot manipulate, full audit trail, automatic rollback, and hard stop conditions. Optimizing usage alone, or letting the evaluator rewrite its own evidence, does not satisfy that contract.

**Exit criteria**: The study protocol, cost-allocation rule, quality criteria, and stopping/reporting rules are written before the comparison is examined; reported group totals, effect estimates, uncertainty, exclusions/missingness, and quality outcomes are reproducible from retained evidence; preparation, retry, observer, and maintenance costs are included; a measured disadvantage is reported as readily as a benefit, with the smallest next measurement recorded. No automatic context or memory change follows from a favorable report.

## Key Risks & Mitigations

- **Double counting cumulative counters, cache subsets, or parent/child calls** → Per-provider accounting schemas and reconciliation tests in M1 before any predictor runs.
- **Hindsight or future leakage into forecasts** → Mandatory receiving-ledger identity and ingestion-position cutoff on every checkpoint and forecast, with ingestion time recorded alongside; grouped chronological splits keeping task lineages together.
- **Stale docs causing agents to repeat "no token evidence"** → M0 stale-doc remediation list + mandatory reporting rules in `AGENTS.md`.
- **Observers mutating or slowing the active workspace** → Read-only observers by default; isolated git worktrees for any M4 verification check; hard cost/invocation budgets.
- **Process identity collisions across hosts or restarts** → Observed `(host_slug, process_start_time, pid)` tuple plus parent links where available; explicit unknowns otherwise, with namespaced source event/session or generation/offset identity for deduplication and coverage gaps when stable identity is unavailable.
- **Accidental commit of operational telemetry to a public repo** → Pre-persistence redaction, an external data directory chosen in M0 (outside the checkout and live sync folders), `.gitignore` guards, and M0–M2 fixture sanitization checks.
